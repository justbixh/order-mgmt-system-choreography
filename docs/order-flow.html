Event-driven order management

How an order moves through the system

Four small services place, stock, pay for and announce an order. They never call each other. They only publish events to Kafka and react to the events they care about.

Order Service Inventory Service Payment Service Notification Service

No central boss

Each service reacts to events and publishes new ones. Nobody orchestrates the order. This style is called saga choreography.

One database each

Order, inventory, payment and notification data live in four separate PostgreSQL databases. The only shared thing is the event stream.

Failures are events too

"Out of stock" and "card declined" are normal business outcomes, so they travel as events. A crashed gateway is a technical failure and goes through retries.

Diagram 3 · When things go wrong

Compensation: undoing what already happened

You cannot roll back across four databases, so the system undoes work with more events. One rule keeps it simple: OrderCancelled is the only compensation trigger. Whoever holds something for that order (stock, money) releases it when they see it.

Out of stock

Order more items than exist
  1. Order publishes OrderCreated
  2. Inventory cannot reserve, publishes InventoryReservationFailed
  3. Order cancels the order, publishes OrderCancelled
  4. Notification tells the customer. Nothing was charged, so there is nothing to refund.

Card declined

Payment token tok_declined or tok_insufficient_funds
  1. Inventory reserved the stock: InventoryReserved
  2. Payment is declined, publishes PaymentFailed
  3. Order cancels, publishes OrderCancelled
  4. Inventory releases the reserved stock: InventoryReleased
  5. Notification tells the customer.

Reservation expires

Stock is held but no payment ever arrives
  1. Inventory's expiry job finds a reservation older than the TTL (default 2 minutes) and publishes InventoryReservationExpired
  2. Order cancels, publishes OrderCancelled
  3. Inventory releases the stock for good.

Paid order is cancelled

Money has already been taken
  1. Order publishes OrderCancelled
  2. Payment sees it and refunds: PaymentRefunded
  3. Inventory releases the stock: InventoryReleased

Gateway outage

Payment token tok_gateway_error
  1. Payment cannot reach the gateway. This is a technical failure, so it throws instead of publishing an event.
  2. The consumer retries with backoff.
  3. If it still fails, the message is parked on payment-events.DLT to inspect in Kafka UI.

Why handlers check the order's current status first. Kafka can deliver an event twice, late, or across topics in a different order than it was produced. A handler that is told "payment succeeded" for an order that is already cancelled must not resurrect it.

Diagram 4 · Inside one service

How events leave and enter safely

The shared messaging-support library gives every service the same plumbing, so the events never get lost or processed twice.

Business failures such as a declined card never reach the red path. They are published as ordinary events (PaymentFailed) and the handler finishes normally.

Where to look in the repo

Seven standalone Maven modules

There is no parent pom. Each module builds on its own, and the shared libraries must be installed first.

events-contractThe wire format. EventType maps each event to its topic and payload class.
messaging-supportOutbox, publisher, idempotent processor, dispatcher, retry and DLT config.
testing-supportTestcontainers (Postgres, Kafka) and a small Kafka test client.
order-serviceOrderSagaHandler decides confirm or cancel from the events it hears.
inventory-serviceReservationService reserves, commits and releases stock.
payment-serviceCharges through a mock gateway and refunds on cancellation.
notification-serviceReacts to order outcomes and logs customer messages.
See it run

Try it yourself

docker compose up -d --build   # Kafka, Postgres, Jaeger and the four services
scripts/demo.sh                # runs every scenario above and checks the results

While it runs, open Kafka UI at localhost:8090 to watch events land on the topics, and Jaeger at localhost:16686 to follow one order across all four services.
