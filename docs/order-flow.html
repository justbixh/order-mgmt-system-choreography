Event-driven order management Coordination style: choreography

How an order moves through the system

Four small services place, stock, pay for and announce an order. They never call each other. They only publish events to Kafka and react to the events they care about. That style is called choreography.

No central boss

Each service reacts to events and publishes new ones. Nobody orchestrates the order. This style is called saga choreography.

One database each

Order, inventory, payment and notification data live in four separate PostgreSQL databases. The only shared thing is the event stream.

Failures are events too

"Out of stock" and "card declined" are normal business outcomes, so they travel as events. A crashed gateway is a technical failure and goes through retries.

New to these terms?

There are two common ways to coordinate a multi-step process across services.

Choreography this system

No service is in charge. Each one reacts to events published by the others and decides its own next step. The flow exists only as the sum of those reactions.

Orchestration not used here

One service owns the flow. It sends commands to the others, waits for their replies, and decides what happens next, including the undo.

How to tell them apart in this repo. Events are past-tense facts: OrderCreated, PaymentFailed. Commands are imperatives: ReserveStock, ChargePayment. Every arrow in Part 1 is an event, so Part 1 is choreography. Part 2 shows orchestration and REST for contrast only.

Diagram 3 · When things go wrong Choreography

Compensation: undoing what already happened

You cannot roll back across four databases, so the system undoes work with more events. One rule keeps it simple: OrderCancelled is the only compensation trigger. Whoever holds something for that order (stock, money) releases it when they see it.

Out of stock

Order more items than exist
  1. Order publishes OrderCreated
  2. Inventory cannot reserve, publishes InventoryReservationFailed
  3. Order cancels the order, publishes OrderCancelled
  4. Notification tells the customer. Nothing was charged, so there is nothing to refund.

Card declined

Payment token tok_declined or tok_insufficient_funds
  1. Inventory reserved the stock: InventoryReserved
  2. Payment is declined, publishes PaymentFailed
  3. Order cancels, publishes OrderCancelled
  4. Inventory releases the reserved stock: InventoryReleased
  5. Notification tells the customer.

Reservation expires

Stock is held but no payment ever arrives
  1. Inventory's expiry job finds a reservation older than the TTL (default 2 minutes) and publishes InventoryReservationExpired
  2. Order cancels, publishes OrderCancelled
  3. Inventory releases the stock for good.

Paid order is cancelled

Money has already been taken
  1. Order publishes OrderCancelled
  2. Payment sees it and refunds: PaymentRefunded
  3. Inventory releases the stock: InventoryReleased

Gateway outage

Payment token tok_gateway_error
  1. Payment cannot reach the gateway. This is a technical failure, so it throws instead of publishing an event.
  2. The consumer retries with backoff.
  3. If it still fails, the message is parked on payment-events.DLT to inspect in Kafka UI.

Why handlers check the order's current status first. Kafka can deliver an event twice, late, or across topics in a different order than it was produced. A handler that is told "payment succeeded" for an order that is already cancelled must not resurrect it.

Diagram 3b · The same decline as a sequence Choreography

Nobody told Inventory to undo anything. It saw OrderCancelled and released the stock on its own. That single compensation trigger is what keeps the design simple.

Good at

  • Services stay independent: adding a consumer needs no change to the producer
  • Survives a service being down, because events wait in Kafka
  • Little coupling beyond the event contract

Costs

  • The flow is hard to see in one place
  • Needs the outbox, idempotent consumers and retries
  • Eventual consistency: the final status arrives later

Choreography · REST Hypothetical

Each service calls the next one

Without a broker, "reacting" means being called. The only way to make the next step happen is for each service to call its successor: Order calls Inventory, Inventory calls Payment, Payment calls Order back to confirm, and Order calls Notification. Nobody is in charge, but everybody has to know who comes next.

Happy path

Solid arrows are requests and dashed arrows are responses. The tall bars show who is busy or blocked. Every caller stays blocked until the call below it returns.

Card declined

A decline unwinds neatly because each caller undoes its own work on the way back. A timeout is the hard case: the caller cannot tell whether the work happened.

The webhook variant. Each call can return 202 Accepted straight away, and the next service calls a callback URL when it finishes. That removes the long open request. In exchange, every sender must now store callback URLs, retry failed deliveries and handle duplicates, which slowly re-invents a message broker.

Good at

  • No extra infrastructure beyond HTTP
  • Failures unwind naturally up the call chain
  • Easy to run and debug locally

Costs

  • Every service must know its successor, which is hidden coupling
  • Long chains multiply latency and failure risk
  • One slow service blocks every caller above it
Orchestration · Kafka Hypothetical

An orchestrator sends commands and waits for replies

The Order Service gains a saga orchestrator that stores the state of each order's saga in its database. Instead of events that describe what happened, it sends commands that say what to do, and the participants answer with replies. Inventory and Payment no longer listen to each other.

Happy path

The client still gets an immediate answer, because the saga runs asynchronously behind the saved order. The commands and replies travel on Kafka, so the outbox, idempotent consumers and retries from the repo are still needed.

Card declined

Compensation becomes an explicit step. The orchestrator knows the stock was reserved, so it sends ReleaseStock and records the saga as COMPENSATING until the reply arrives.

Good at

  • The whole flow and its state are readable in one place
  • Easy to add branches, timeouts and manual steps
  • Participants stay simple: handle a command, send a reply

Costs

  • The orchestrator knows every step and can become a bottleneck for change
  • Needs commands and replies on top of the existing events
  • One more thing to keep correct and to restart safely
Orchestration · REST Hypothetical

One service calls the others in order

The Order Service becomes the boss: it calls Inventory, then Payment, then Notification over HTTP, one after another, and the client waits for the whole chain.

Happy path

Solid arrows are requests, dashed arrows are responses. The Client and Order bars stay open the whole time, so latency is the sum of all the calls.

Card declined

The stock is already reserved, so the Order Service must undo it by calling Inventory again. In the Kafka versions that is a reaction or a command. Here it is code the caller has to remember to write.

If Payment times out instead of answering, the Order Service cannot tell whether the card was charged. Handling that safely needs retries with idempotency keys.

Good at

  • The simplest to write and to follow
  • One request, one stack trace
  • The client gets a final answer in one call

Costs

  • Tight coupling: Order must know every service and all must be up
  • Latency is the sum of every call
  • Hand-written rollbacks that can fail too

When I would pick which

  • A short, stable flow of three or four steps, or learning event-driven design: choreography over Kafka. This is the repo.
  • A flow that keeps growing, with branches, timeouts or manual approvals: orchestration over Kafka, either a hand-written state machine or a workflow engine such as Temporal or Camunda.
  • Everything deployed together, low volume, simplicity first: orchestration over REST.
  • Choreography over REST: rarely the best option. If you find yourself building it, consider an orchestrator or a broker instead.

Hybrids are normal. Real order systems often run the core saga in an orchestrator and still publish events so that other services, such as notifications and analytics, can subscribe without the orchestrator knowing about them.

Where to look in the repo

Seven standalone Maven modules

There is no parent pom. Each module builds on its own, and the shared libraries must be installed first.

events-contractThe wire format. EventType maps each event to its topic and payload class.
messaging-supportOutbox, publisher, idempotent processor, dispatcher, retry and DLT config.
testing-supportTestcontainers (Postgres, Kafka) and a small Kafka test client.
order-serviceOrderSagaHandler decides confirm or cancel from the events it hears.
inventory-serviceReservationService reserves, commits and releases stock.
payment-serviceCharges through a mock gateway and refunds on cancellation.
notification-serviceReacts to order outcomes and logs customer messages.
